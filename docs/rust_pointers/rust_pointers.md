# Rust 指针类型全景解析

## 设计背景与问题域

Rust 没有像 C 那样单一的"指针"概念。取而代之的是一整套**编码了不同所有权语义的引用类型**。理解这套体系的关键问题是：

1. **为什么 Rust 需要这么多种"指针"？** Java 只有对象引用，C 只有 `*T`。
2. **每种指针的核心语义是什么？** 不是"指向内存的地址"，而是"谁拥有这块内存、谁能修改、能跨线程吗"。
3. **如何选择正确的指针类型？** 这是 Rust 编码时最频繁的决策之一。

Rust 的设计哲学是：**让资源管理的语义在类型中显式化**。每种指针类型都是一份契约，编译器根据这份契约执行相应的安全检查。

---

## Rust 的指针类型总览

| 类型 | 所有权 | 可变性 | 线程安全 | 大小（64位）| 核心语义 |
|------|--------|--------|---------|------------|---------|
| `&T` | 借用 | 不可变 | 是（T: Sync）| 8B | 只读访问，不拥有 |
| `&mut T` | 借用 | 可变 | 是（T: Send）| 8B | 独占写访问，不拥有 |
| `Box<T>` | 独占 | 可变 | 是（T: Send）| 8B | 堆分配，单一所有者 |
| `Rc<T>` | 共享 | 不可变 | 否 | 8B | 单线程引用计数共享 |
| `Arc<T>` | 共享 | 不可变 | 是 | 8B | 多线程原子引用计数共享 |
| `RefCell<T>` | — | 内部可变 | 否 | ~24B+ | 运行时借用检查 |
| `Cell<T>` | — | 内部可变 | 否 | ~24B+ | Copy 类型的运行时替换 |
| `Mutex<T>` | — | 内部可变 | 是 | ~40B+ | 互斥锁保护的访问 |
| `*const T` | 无 | 不可变 | 否 | 8B | 不安全的原始指针 |
| `*mut T` | 无 | 可变 | 否 | 8B | 不安全的原始指针 |
| `fn(T) → U` | — | — | 是 | 8B | 函数指针 |
| `&dyn Trait` | 借用 | — | 取决于T | 16B | 胖指针（动态分发）|

**关键洞察**：在 Rust 中，"指针类型" = "内存地址" + "所有权语义" + "安全检查策略"。这不是过度设计，而是将 Java 中隐式的 GC 语义、C 中缺失的安全检查，显式编码到类型系统中。

## 逐类深入解析

### 1. 引用（&T / &mut T）：借用检查器的基石

引用是 Rust 中最基础的"指针"，但它们**不是指针**——它们是**借用（borrow）**。

```rust
let s = String::from("hello");
let r = &s;      // 不可变借用：承诺"我只读，不修改"
let m = &mut s;  // 编译错误！s 已被不可变借用，不能可变借用
```

**编译期检查（零运行时开销）**：
- 多个 `&T` 可以同时存在（读者并行）
- 一个 `&mut T` 独占存在（写者独占）
- 引用不能比被引用的值活得更长（生命周期检查）

**与 Java 对比**：
- Java 的引用没有可变性约束，任何持有者都可以修改对象（除非字段是 `final`）
- Java 没有生命周期概念，GC 保证对象在最后一个引用消失前不被释放
- Rust 的引用在编译期就消除了数据竞争和垂悬指针

### 2. Box<T>：堆分配的独占所有权

`Box<T>` 是 Rust 中最接近 "new" 的操作，但它明确表达了**独占所有权**。

```rust
let b = Box::new(String::from("hello"));
// b 拥有这个 String。当 b 离开作用域时，String 被 drop，堆内存释放。
```

**设计意图**：
- **递归类型**：`enum List { Cons(i32, Box<List>), Nil }` —— Box 打破了递归类型的无限大小问题
- **动态分发**：`Box<dyn Trait>` —— 编译时不知道具体类型，运行时通过 vtable 分派
- **大对象**：栈空间有限（通常几 MB），Box 将数据移到堆上

**内存布局**：
```
栈上的 Box<String>（8 bytes）：
┌─────────────────┐
│  堆指针          │ ──→ 堆上的 String 数据
└─────────────────┘
```

对比 Java：
- Java 的 `new String("hello")` 也在堆上分配，但返回的是引用（可以多个变量共享）
- Rust 的 `Box::new(...)` 返回的是独占所有权（只有一个变量能拥有它）

### 3. Rc<T>：单线程共享所有权

当数据需要被**多个部分长期共享**时，使用 `Rc<T>`（Reference Counted）。

```rust
let data = Rc::new(vec![1, 2, 3]);
let data2 = Rc::clone(&data); // 引用计数 +1，不是深拷贝

// data 和 data2 都指向同一个 Vec
println!("{}", Rc::strong_count(&data)); // 2
```

**内存布局**：
```
栈上的 Rc<T>（8 bytes）：
┌─────────────────┐
│  指向堆的指针     │ ──→ 堆上的控制块：[引用计数, 弱引用计数, T 的数据]
└─────────────────┘
```

**关键限制**：
- `Rc` 是不可变的。如果需要修改共享数据，需要配合 `RefCell`（见下文）
- `Rc` 不是线程安全的（引用计数不是原子操作）
- `Rc` 可能导致循环引用内存泄漏（需要用 `Weak` 打破循环）

**与 Java 对比**：
- Java 的对象默认就是 `Rc` 语义（多个引用 + GC）
- Rust 的 `Rc` 需要显式选择，且有确定性析构（引用计数归零时立即释放）

### 4. Arc<T> + Mutex<T> / RwLock<T>：多线程共享可变

`Arc<T>`（Atomic Reference Counted）是 `Rc` 的线程安全版本，使用原子操作维护引用计数。

```rust
let counter = Arc::new(Mutex::new(0));
let counter2 = Arc::clone(&counter);

std::thread::spawn(move || {
    let mut num = counter2.lock().unwrap();
    *num += 1;
});
```

**组合语义**：
- `Arc<T>`：线程安全的共享所有权
- `Mutex<T>`：互斥锁，保证同一时间只有一个线程能访问 T
- `RwLock<T>`：读写锁，允许多个读者或一个写者

**编译器保证**：
- `Arc` 要求 `T: Send + Sync` 才能跨线程共享
- `MutexGuard`（`lock()` 的返回值）实现 `DerefMut`，允许修改内部数据
- 锁在 `MutexGuard` 离开作用域时自动释放（RAII）

**与 Java 对比**：
- Java：`synchronized(obj) { obj.count++; }` —— 运行时锁，编译器不检查是否正确使用
- Rust：`*counter.lock().unwrap() += 1` —— 编译器保证你无法在无锁的情况下访问数据

### 5. RefCell<T>：运行时借用检查

`RefCell` 提供了**内部可变性**：即使外部值是不可变的，也可以通过 `RefCell` 在运行时获得可变访问。

```rust
let cell = RefCell::new(String::from("hello"));

// 外部值 cell 本身不是 mut，但内部可以修改
let mut s = cell.borrow_mut(); // 运行时检查
s.push_str(" world");
```

**为什么需要 RefCell？**

编译器的借用检查是**保守的**。有些场景在编译期无法证明安全，但在运行时实际上是安全的：

```rust
// 场景：回调函数需要修改外部状态
let data = RefCell::new(0);
let closure = || {
    *data.borrow_mut() += 1; // 编译器无法静态验证，但运行时我们知道安全
};
```

**运行时检查**：
- `borrow()` → 返回 `Ref<T>`（不可变引用）
- `borrow_mut()` → 返回 `RefMut<T>`（可变引用）
- 如果同时存在 `borrow()` 和 `borrow_mut()` → **panic**（不是编译错误！）

**与编译期借用的对比**：

| 维度 | `&T` / `&mut T` | `RefCell<T>` |
|------|------------------|---------------|
| 检查时机 | 编译期 | 运行时 |
| 违反后果 | 编译错误 | panic |
| 性能 | 零开销 | 引用计数 + 检查 |
| 适用场景 | 绝大多数情况 | 编译器无法验证的场景 |

### 6. Cell<T>：Copy 类型的轻量内部可变性

`Cell` 是比 `RefCell` 更轻量的内部可变性，但**只适用于实现了 Copy trait 的类型**（如 `i32`、`bool`、`char`）。

```rust
let cell = Cell::new(42);
cell.set(100);      // 替换值
let val = cell.get(); // 拷贝出值（不是引用）
```

**原理**：`Cell` 从不返回引用，而是**整体拷贝或替换值**。因此不存在同时存在多个引用的问题，不需要运行时检查。

**适用场景**：
- 计数器、标志位等简单状态
- 需要内部可变性的回调计数器
- 不需要 `RefCell` 的引用语义时的性能优化

### 7. 原始指针（*const T / *mut T）：不安全的 C 指针

原始指针是 Rust 中最接近 C 指针的类型，**不受借用检查器约束**。

```rust
let x = 42;
let r = &x as *const i32; // 从引用创建原始指针

unsafe {
    println!("{}", *r); // 解引用必须在 unsafe 块中
}
```

**特点**：
- 可以为 null
- 可以悬空（指向已释放内存）
- 可以进行指针算术运算
- 可以有多个 `*mut` 指向同一地址（不检查别名）

**使用场景**：
- FFI（与 C 代码交互）
- 实现底层数据结构（如自定义内存分配器）
- 性能极度敏感的场景（绕过借用检查器的保守假设）

**安全保证**：
Rust 不保证原始指针的安全——**unsafe 块的正确性完全由程序员负责**。但一旦从原始指针创建安全的引用（`&T`），编译器会重新检查其使用是否合法。

### 8. 函数指针（fn(T) → U）

函数指针指向具体的函数地址，**不捕获环境**。

```rust
fn add_one(x: i32) -> i32 { x + 1 }

let f: fn(i32) -> i32 = add_one;
f(5); // 调用
```

**与闭包的区别**：

| 维度 | `fn(T) → U` | `impl Fn(T) → U` |
|------|-------------|-----------------|
| 捕获环境 | 不能 | 可以 |
| 大小 | 固定 8 bytes | 不固定（由捕获变量决定）|
| 强制转换 | 可以隐式转换 | 每个闭包是独立类型 |
| 存储 | 可以直接存储 | 需要 `Box` 或泛型参数 |

## 选择指南：我该如何选择指针类型？

### 决策树

```
数据需要在堆上吗？
├─ 否（栈上足够）→ 直接使用值类型 T
└─ 是 → 需要共享吗？
    ├─ 否（单一所有者）→ Box<T>
    └─ 是 → 需要跨线程吗？
        ├─ 否（单线程）→ Rc<T>
        │               └─ 需要修改？→ Rc<RefCell<T>>
        └─ 是（多线程）→ Arc<T>
                        └─ 需要修改？→ Arc<Mutex<T>> 或 Arc<RwLock<T>>

数据在栈上但需要内部可变？
└─ T 实现了 Copy？→ Cell<T>
   └─ T 未实现 Copy？→ RefCell<T>

与 C 代码交互？
└─ *const T 或 *mut T（unsafe）
```

### 常用组合速查

| 场景 | 推荐类型 | 说明 |
|------|---------|------|
| 简单堆分配 | `Box<T>` | 链表节点、树节点、大对象 |
| 单线程共享只读 | `Rc<T>` | 配置对象、共享缓存 |
| 单线程共享可变 | `Rc<RefCell<T>>` | 观察者模式、图结构 |
| 多线程共享只读 | `Arc<T>` | 跨线程共享配置 |
| 多线程共享可变 | `Arc<Mutex<T>>` | 计数器、共享状态 |
| 多线程多读少写 | `Arc<RwLock<T>>` | 读多写少的缓存 |
| 回调计数器 | `Cell<usize>` | 轻量内部可变性 |
| 动态分发 | `Box<dyn Trait>` | 工厂模式、策略模式 |
| FFI | `*mut T` | unsafe，需手动保证安全 |

## 内存布局对比

### 各种指针的栈上大小

```rust
println!("&T          = {} bytes", std::mem::size_of::<&String>());
println!("Box<T>      = {} bytes", std::mem::size_of::<Box<String>>());
println!("Rc<T>       = {} bytes", std::mem::size_of::<Rc<String>>());
println!("Arc<T>      = {} bytes", std::mem::size_of::<Arc<String>>());
println!("*const T    = {} bytes", std::mem::size_of::<*const String>());
println!("fn(T)→U     = {} bytes", std::mem::size_of::<fn()->()>());
println!("&dyn Trait  = {} bytes", std::mem::size_of::<&dyn std::fmt::Debug>());
```

输出（64 位系统）：
```
&T          = 8 bytes
Box<T>      = 8 bytes
Rc<T>       = 8 bytes
Arc<T>      = 8 bytes
*const T    = 8 bytes
fn(T)→U     = 8 bytes
&dyn Trait  = 16 bytes（胖指针）
```

**为什么大多数指针都是 8 bytes？** 因为它们在栈上只存一个地址。`Rc`、`Arc` 的引用计数存在堆上，不在栈指针里。

## 与 Java/Go 的对比

| Rust 类型 | 最接近的 Java 概念 | 最接近的 Go 概念 | 核心差异 |
|-----------|------------------|----------------|---------|
| `&T` | 不可变引用（没有直接对应）| 值传递的指针 | Rust 编译期检查可变性 |
| `&mut T` | 没有直接对应 | 没有直接对应 | Rust 独占可变保证 |
| `Box<T>` | `new T()` | `&T`（逃逸到堆）| Rust 确定性析构 |
| `Rc<T>` | 对象引用（GC 管理）| 指针（GC 管理）| Rust 引用计数，立即释放 |
| `Arc<T>` | 没有直接对应 | 没有直接对应 | Rust 显式选择线程安全 |
| `RefCell<T>` | `AtomicReference` | 没有直接对应 | Rust 运行时借用检查 |
| `Mutex<T>` | `synchronized` | `sync.Mutex` | Rust 编译期保证正确使用 |
| `*const T` | C JNI 指针 | `unsafe.Pointer` | Rust 必须在 unsafe 块中使用 |

## 设计哲学总结

### Rust 没有"指针"，只有"所有权语义"

Java 只有对象引用，GC 负责所有内存管理。C 只有 `*T`，程序员负责所有内存管理。Rust 选择了第三条路：**用类型系统编码所有权语义**。

```rust
&T      → "我借用这块内存，保证不修改"
&mut T  → "我独占借用这块内存，保证不共享"
Box<T>   → "我拥有这块堆内存，离开时释放"
Rc<T>   → "我们共享这块内存，计数归零时释放"
Arc<T>  → "我们跨线程共享这块内存"
RefCell  → "编译器无法验证时，运行时检查借用规则"
Cell     → "我只存 Copy 类型，不需要引用语义"
*const T → "我知道自己在做什么，不需要编译器检查"
```

### 这不是过度设计，而是显式化

Java 的引用也有隐含的所有权语义——只是这些语义被 GC 掩盖了：
- "这个对象还有引用吗？" → GC 在运行时扫描
- "这个引用是唯一的吗？" → Java 不知道，也不关心
- "多个线程同时修改安全吗？" → 运行时发现数据竞争

Rust 把这些**隐式假设显式化**到类型中。代价是编码时需要选择正确的类型，收益是编译器可以在编译期消除整类 bug。

> **核心洞察**：Rust 的指针类型体系不是 C 的"内存地址 + 不安全操作"，也不是 Java 的"统一引用 + GC"。它是**类型系统级别的资源管理契约**——每个类型都精确描述了"谁拥有、谁能访问、何时释放、是否线程安全"。这就是 Rust "零成本抽象 + 编译期安全"的技术基础。
